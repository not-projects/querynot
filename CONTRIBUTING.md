# Contributing to QueryNot

QueryNot welcomes reproducible bug reports, focused feature proposals, review feedback, and agent-ready task definitions.

This repository accepts **AI-generated contributions only**. Humans are welcome to define work, curate prompts, review output, request revisions, validate behavior, and merge changes, but repository content submitted in pull requests must be generated by AI tooling rather than handwritten line by line.

If that workflow does not fit your contribution, open an issue instead of a pull request.

## Before You Start

Read:

- [README.md](README.md)
- [AGENTS.md](AGENTS.md)
- [CHANGELOG.md](CHANGELOG.md)
- [SECURITY.md](SECURITY.md)

Then search existing issues before opening a bug report, feature request, or agent task.

## Accepted Contributions

Good contributions include:

- reproducible bug reports with secrets and private data removed
- feature requests grounded in a concrete database workflow
- bounded implementation tasks with explicit acceptance criteria
- AI-generated pull requests with human review and validation evidence
- documentation updates that keep public claims aligned with shipped behavior

## AI-Generated Contribution Rules

Every pull request must:

- contain AI-generated repository changes
- name the agent or AI tool used
- summarize the prompt or task given to the agent
- receive human review before submission
- avoid copied material with incompatible licensing
- disclose known risks, skipped validation, and uncertain generated output

Maintainers may close contributions that appear manually authored, omit authorship disclosure, or contain effectively unreviewed generated output.

## Workflow

1. Start from the latest `master` branch.
2. Link an existing issue or open one with enough detail for an agent to execute safely.
3. Keep the change focused; do not combine unrelated features, refactors, or release work.
4. Update [CHANGELOG.md](CHANGELOG.md) under `Unreleased` for user-visible changes.
5. Keep [README.md](README.md), [AGENTS.md](AGENTS.md), and future architecture documentation aligned with actual behavior.
6. Run every relevant checked-in validation command.
7. Complete the pull-request template, including AI authorship and validation evidence.

## Validation

QueryNot does not yet have an application scaffold or canonical build commands. Once commands are checked into project configuration, [AGENTS.md](AGENTS.md) becomes the operational source of truth.

Do not copy commands from another project and present them as validated QueryNot commands.

## Database Safety

- Never commit connection strings, passwords, tokens, private certificates, production data, or unredacted logs.
- Use synthetic or disposable databases for tests and examples.
- Treat destructive SQL, credential handling, TLS behavior, exports, and persisted history as security-sensitive work.
- Do not introduce telemetry, cloud synchronization, or remote services without explicit issue-level approval.
- Avoid tests that can discover or connect to databases outside their isolated fixtures.

## Pull-Request Expectations

Every pull request should include:

- a linked issue
- a concise summary
- validation commands and results
- screenshots or recordings for visible UI changes
- security and data-handling impact
- known risks or deferred work
- documentation and changelog impact
- AI tool and task disclosure

## Security

Do not disclose suspected vulnerabilities in public issues or pull requests. Follow [SECURITY.md](SECURITY.md).
